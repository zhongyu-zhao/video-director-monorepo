# 小说扩写 / 改编为视频剧本调研（2026-11）

**调研问题**：做一个把现有小说（或故事大纲）扩写、改编成可拍摄视频剧本的 agent 子 repo，当前有哪些可复用的方法、论文、开源实践和格式标准？系统边界应该怎么划，哪些环节交给模型、哪些必须由代码保证？

**范围**：以叙事文本 → 场景剧本为主，覆盖结构方法、LLM 改编研究、剧本格式、短剧/剧集/电影的体量差异和评测；不展开视频生成、分镜绘制和最终渲染。

**数据快照**：2026-11-22。论文指标来自各自 benchmark，不能横向比较；GitHub 项目只代表可参考的实现形态，不代表工程质量。

---

## 0. 一页结论

1. **改编不是“把小说压短”，而是换媒介。** 小说的叙述、心理描写、时间跳跃和作者视角，必须被翻译成可拍摄的动作、对白、场景和视听信息。只做文本摘要的系统会得到“故事梗概”，不是剧本。
2. **LLM 研究的共同答案是分层，而不是把整本书塞进一个 prompt。** Dramatron 用 premise → characters → beats → scenes → dialogue 的 prompt chaining；R² 用滑窗阅读 + 因果情节图 + 场景大纲再写剧本；MovieSum 证明长剧本理解本身仍是难题。分层既为上下文预算，也为可核对。
3. **改编系统最需要的是“可追溯的计划”，不是一次性正文。** 每一场戏应该能回到原文的哪一段、对应哪个结构节拍、目标时长多少、有谁出场。没有这层，模型跑偏后无法定位、无法局部重写、无法验收。
4. **结构方法是脚手架，不是创作判断。** 三幕、Save the Cat 15 拍、序列法、短剧的“钩子—升级—反转—卡点”都可以转成百分比/区间，用来检查节奏和分配场次；它们不能替作者决定人物和主题。
5. **短剧是独立品类，规则与电影/长剧不同。** 行业实践给出的体量锚点：45 分钟长剧约 1.5 万字/集，10–15 分钟短剧约 3500 字/集，1–2 分钟微短剧约 500 字/集；微短剧通常 60–90 秒就要有一个爆点或亮点。竖屏、场景集中、人物集中、每集卡点是硬约束。
6. **自动评测没有单一可靠指标。** 可确定计算的是覆盖率、场次/时长、人物一致性、格式；语义质量只能靠 LLM 评审 + 人工抽读。CML-Bench 把电影剧本质量拆成对白连贯、人物一致、情节合理三维，是目前较可操作的参考。
7. **长程一致性仍是主要失败模式。** STAGE 在 151 部中英文完整剧本上发现：递归状态更新会“静默遗忘”，跨场推理弱，角色扮演在风格忠实与剧本记忆之间取舍。改编越长，越需要把人物状态、已知信息和情节线显式落盘。
8. **推荐形态：确定性改编内核 + 逐场写作器 + 硬门验收。** 代码负责解析章节、切分原文、分配场次/时长、抽人物、套结构、检查覆盖与格式；LLM/人负责把每场写成动作和对白。`adaptation.json` 是事实源，Fountain/Markdown 只是视图。
9. **M0 先做“可核对的改编计划 + 可导入/生成的逐场草稿 + 验收”，不做一键成片。** 先把覆盖、场次、人物、时长、格式和来源锚点做对，再谈对白质量和风格。

## 1. 问题拆解：小说和剧本到底差在哪

### 1.1 媒介差异

| 维度 | 小说 | 视频剧本 |
|---|---|---|
| 信息载体 | 叙述、心理、作者评论、修辞 | 可见动作、对白、声音、画面 |
| 时间 | 可自由跳过、倒叙、概述 | 按场组织，观众实时经历 |
| 视角 | 可进入任意人物内心 | 只能拍外部行为，或靠表演/旁白 |
| 单位 | 章、段、句 | 场（scene）、序列、幕、集 |
| 篇幅锚点 | 字数 | 1 页剧本 ≈ 1 分钟成片（西式格式的常用估算） |
| 冗余 | 可大量铺垫 | 每场都要有功能，否则被剪 |

改编的核心动作是 **externalize**：把“她忽然明白自己被利用了”翻译成她看到什么、做了什么、对谁说了什么。无法外化的内容要么删，要么改成视觉母题/旁白/字幕，并明确标注为新增。

### 1.2 两种任务，不要混为一谈

- **改编（adapt）**：源文本密集，主要问题是选择、压缩、重排、视角转换。一个 100 万字的网文改编成 80 集微短剧，首先要决定保留哪条主线、删哪些支线。
- **扩写（expand）**：源文本稀疏（大纲、短篇、几句话的设定），主要问题是补人物前史、补冲突过程、补对白和场面，同时不改变原有事实。扩写比改编更容易幻觉，因为模型有大量空白要填。

两者可以共用一条流水线，但验收重点不同：改编看“有没有丢关键情节”，扩写看“新增内容有没有越权改设定”。

### 1.3 一个合格交付物应包含什么

不是一段“剧本正文”，而是：

- **改编计划**：场次表、每场来源锚点、集/幕归属、目标时长、出场人物、结构节拍。
- **人物表**：姓名、别名、首次/末次出现、对白量、来源（自动抽取/人工指定）。
- **逐场草稿**：场景头（内/外、地点、日/夜）、动作、对白、转场。
- **来源映射**：每场对应原文的句子/段落范围；新增对白标注 `adapted` / `invented`。
- **验收报告**：覆盖率、场次/时长、人物一致性、格式、估算时长、风险项。
- **可编辑导出**：JSON（事实源）+ Fountain/Markdown（人读和进入下游）。

## 2. 可复用的结构方法

### 2.1 三幕与 Save the Cat 15 拍

Save the Cat 把长片拆成 15 个节拍，并给出大致百分比：Opening Image（0–1%）、Theme Stated（5%）、Set-Up（1–10%）、Catalyst（10%）、Debate（10–20%）、Break into Two（20%）、B Story（22%）、Fun & Games（20–50%）、Midpoint（50%）、Bad Guys Close In（50–75%）、All Is Lost（75%）、Dark Night of the Soul（75–80%）、Break into Three（80%）、Finale（80–99%）、Final Image（99–100%）。这些百分比可以直接变成场次归属的区间，用来检查“中点和第三幕是不是空/挤”。

注意：节拍表是商业长片的一种经验结构，不是唯一正确结构；对文艺片、群像、短剧要换模板。系统应把模板做成数据，而不是把某一套写死。

### 2.2 场（scene）的最小定义

一个可拍摄的场至少要有：地点、时间、在场人物、一个目标/冲突、一个状态变化（turn）。剧本写作里常用的检查是“这场删掉，故事是否受损”。LLM 生成时最常见的坏场是“两个人复述观众已知的信息”或“只有氛围没有变化”。

工程上可以检查的弱信号：场里有没有人物、有没有对白、有没有状态变化标记（计划里可留空给人填）、时长是否异常。不能自动判断“好不好”，但能逼作者/模型给出结构。

### 2.3 序列法

把长片分成 8 个序列（约 12–15 分钟一个），每个序列有自己的小高潮。对剧集尤其有用：一集可以是一个序列，集内再分场。它对“每集要有钩子和卡点”的短剧更自然。

### 2.4 短剧/微短剧的特殊规则

2024 年网络作家、ShortMax 总编辑梨花颜在创作谈里给出了一组行业体量锚点：45 分钟长剧约 15000 字/集，10–15 分钟短剧约 3500 字/集，1–2 分钟微短剧约 500 字/集；微短剧要求人物集中、主线清晰、冲突强，基本 60–90 秒要有一个爆点或亮点。她还提到：竖屏群像要避免一场里塞太多主角；剧本格式目前没有统一标准，但场次、日夜、内外景、分镜和特写要标清。

对系统的含义：

- 集数和单集时长是最重要的输入约束，直接决定场次数和每场字数。
- 短剧需要 per-episode 结构（开场钩子、升级、反转、结尾卡点），不能只套长片 15 拍。
- 场景预算要倾向可落地：少场景、少群演、少复杂转场；这些应作为 brief 字段，而不是让模型猜。

## 3. LLM 改编研究

### 3.1 Dramatron：分层 prompt chaining

Mirowski 等人的 Dramatron 用语言模型分层生成 title、characters、story beats、location descriptions 和 dialogue，并用 15 位戏剧/电影从业者做了共创研究。结论不是“模型能独立写剧本”，而是：**结构化上下文（先人物、再节拍、再场景、再对白）能显著改善长程连贯性，且人类作者仍然是编辑者**。

对工程的含义：一次调用只写一场，前面已经有 brief、人物表、前后场摘要；不要指望一次调用“写完整本”。

### 3.2 R²：Reader–Rewriter + 因果情节图

R²（2025）把小说改编拆成两个模块：Reader 用滑窗读长文、构建带因果关系的 plot graph；Rewriter 先生成场景大纲、再生成剧本。它还针对幻觉做了 hallucination-aware refinement，并用 greedy cycle-breaking 处理情节图中的环。论文报告在 pairwise 人工/模型比较中，相对三个基线在 GPT-4o 总体胜率上有 51.3%、22.6%、57.1% 的绝对提升。

可借鉴的点：**先情节图/场景大纲，再正文**；长文必须滑窗；因果边比“段落摘要”更能保持前后逻辑。局限：因果图抽取本身会错，且论文没有解决制作约束（时长、场景、演员）。

### 3.3 MovieSum：长剧本仍是长文理解难题

MovieSum（ACL 2024 Findings）包含 2200 部电影剧本和对应的 Wikipedia 剧情摘要，并手工标注了剧本结构元素。它的存在说明：电影剧本比电视剧本长，长上下文理解仍是瓶颈，现有 LLM 在剧本摘要上并不轻松。

对改编的含义：不要用“整本小说 + 一句 prompt”作为主路径；分层摘要/场景化是必要的工程手段，不是优化项。

### 3.4 CML-Bench：把剧本质量拆成三维

CML-Bench（2025）用 Cinematic Markup Language 数据构建评测，提出三个维度：Dialogue Coherence（对白连贯）、Character Consistency（人物一致）、Plot Reasonableness（情节合理）。它同时指出 LLM 生成的剧本“结构像样但缺少灵魂”，并用 instruction 提升结构化程度。

对验收的含义：自动指标可以覆盖“人物是否前后一致、对白是否答非所问、情节是否自洽”，但不能替代人读。系统应把这三类检查做成可复核的 warning，而不是一个总分。

### 3.5 STAGE：长程人物状态是硬问题

STAGE（2026）在 151 部中英文完整剧本上评测人物状态追踪，发现三类失败：递归更新时静默遗忘、跨场推理弱、角色扮演时风格忠实与剧本记忆互相拉扯。

对工程的含义：改编长文时，应该显式维护 **人物状态/已知信息/关系变化**，至少每场记录“谁知道什么、目标是什么、关系变化”。M0 可以先只记录出场人物和来源锚点，但 schema 要留位置。

### 3.6 相关但方向相反的任务

- **ScreenWriter**（2024）从视频生成剧本（对白、说话人、场景断点、视觉描述），并用场景断点做分层摘要。它证明“场景断点 + 分层”是通用结构，但输入方向与改编相反。
- **OmniScript**（2026）做长视频 → 带时间定位的逐场剧本，8B 多模态模型，强调 temporal grounding。可借鉴的是“每场必须有时间/来源锚点”。
- **BookSum** 等长叙事摘要数据集说明：长文的分层摘要/内容选择是成熟问题，但摘要是改编的子步骤，不是改编本身。

### 3.7 风险：偏见与版权

2026 年的 Bechdel 审计比较了 GPT-5、Gemini 3 Pro、Claude Sonnet 4.5 生成的剧本和 768 部人类剧本，发现人类剧本更可能通过 Bechdel 测试，且各类剧本在多数社会网络指标上都有代表性偏差。改编系统不应把“模型默认的人物关系”当成原作的还原。

版权上，小说文本是受版权保护的用户输入：本地处理、不把原文贴到公开 issue/PR、不把大段原文写进日志，是基本边界。

## 4. 开源与产品实践

| 项目/产品 | 形态 | 可借鉴 | 缺口 |
|---|---|---|---|
| [Toonflow / 知剧AI](https://github.com/openfrees/toonflow) | 短剧创作平台：小说转剧本、剧本延展分镜、管理后台、桌面端 | 小说项目 → 章节 → 剧情线 → 剧本的产品流程；短剧场景 | 重平台、重 UI；结构化契约和验收门不是重点 |
| [Wen-Mirror](https://github.com/jntmlol24/Wen-Mirror) | FastAPI + LangChain，3 章以上小说 → YAML 结构化剧本，带 `/extract`、`/generate`、`/chat` | 用 YAML/JSON 作为中间态；兼容 OpenAI 协议端点 | 依赖 LLM 一次性抽取/生成，缺少确定性覆盖检查和来源锚点 |
| 商业 AI 编剧工具（如 Wawa Writer） | 小说转剧本、续写、改写 | 交互式共创、局部重写 | 闭源，无法审计；质量依赖 prompt 和模型 |
| Fountain / FDX 生态 | 剧本纯文本/交换格式 | 人读和下游工具链的通用出口 | 只表达剧本，不表达改编来源、覆盖和计划 |

共同缺口：**没有把“改编计划”当成一等工件**。多数工具直接生成正文，失败时只能整段重来；也没有把“这场从原文哪里来、覆盖了没有、人物有没有越权”做成可执行检查。

## 5. 格式与工件

### 5.1 Fountain

Fountain 是纯文本剧本标记，核心元素包括：title page（`Title:`、`Credit:`、`Author:` 等键值）、scene heading（`INT.` / `EXT.` 开头）、action、character（大写行）、parenthetical、dialogue、transition（以 `TO:` 结尾）、section（`#`）、note（`[[ ]]`）、page break（`===`）。它足够表达 M0 的场景/动作/对白，且可被大量剧本软件导入。

选择 Fountain 作为导出视图的理由：纯文本、diff 友好、无二进制依赖、可读；局限是不能表达分镜、机位、双人对白等高级信息（Fountain 有 dual dialogue `^`，M0 不需要）。

### 5.2 为什么 JSON 是事实源

- 下游（video-director、分镜、TTS）需要结构化字段，而不是解析富文本。
- 校验需要遍历场、人物、来源区间；JSON 比 Fountain 容易。
- Fountain/Markdown 是可重建视图：同一份 JSON 可以导出不同格式，不维护第二份事实。
- schema 必须版本化；破坏性变更要迁移。

### 5.3 时长估算

行业常用“1 页 ≈ 1 分钟”，但中文剧本没有统一页数标准。工程上更稳的是按对白字数/语速 + 动作块数量估算：中文对白约 4 字/秒，英文约 2.5 词/秒；动作按字数/阅读速度估。它只能做量级检查（是否严重超长/不足），不能当精确时长。

## 6. 评测与质量门

### 6.1 可确定计算的

- **来源覆盖**：每个源句子是否至少被一场覆盖；是否有场次无来源锚点。
- **结构**：场次数、每集场次数、时长总和、节拍顺序、场次顺序。
- **人物**：对白说话人是否在人物表；人物首次/末次出现是否合理；是否有未登记的新角色。
- **格式**：场景头、动作/对白非空、转场合法、无空场。
- **篇幅**：每场估算时长与目标时长的偏差；全片总时长偏差。
- **新增披露**：对白标记 `source` / `adapted` / `invented` 的比例。

### 6.2 需要模型/人判断的

- 对白是否像这个人说的（角色声音）。
- 场是否有冲突和状态变化。
- 删掉的情节是否影响理解。
- 主题是否被保留/深化。
- 是否存在刻板印象、版权/合规风险。

### 6.3 质量门策略

参考已有子 repo 的做法：`fail` 阻止交付，`warn` 进入人工复核，`skip` 不算通过。改编内核的 fail 应该只给“结构上不可用”的问题（覆盖断裂、场次缺失、人物越权、格式坏），语义问题给 warn，避免用模型打分决定成败。

## 7. 推荐架构

```text
小说/大纲
  → 解析（章节、段落、句子、字数）
  → 人物抽取（对白归属 + 别名 + 人工覆盖）
  → 改编计划（场次、集、节拍、时长、来源锚点、覆盖）
  → 逐场 brief
  → 写作器（LLM 或人）→ 逐场草稿 JSON
  → 合并 + 验收（覆盖/人物/格式/时长/新增披露）
  → adaptation.json（事实源）+ screenplay.json + Fountain/Markdown + report.json
```

边界：

- **代码**：解析、切分、分配、覆盖、人物校验、格式、导出。
- **模型/人**：每场写什么、怎么外化、对白语气、场景调度。
- **不做**：让模型直接改 `adaptation.json`；让模型一次写完整本；把“通过 LLM 评审”当成验收。

### 7.1 长文策略

- 先按章节/句子切分，场景只引用连续源区间。
- 每场 brief 只带：本场原文、前后场一句话、人物表、结构节拍、目标时长、硬约束。
- 需要跨场信息时，读计划里已落盘的人物/状态，不把全书重新塞进 prompt。
- 逐场草稿落盘，支持断点续跑和只重写某场。

### 7.2 失败模式与对策

| 失败 | 表现 | 对策 |
|---|---|---|
| 幻觉人物 | 出现人物表外的新名字 | 对白说话人必须在人物表；新增角色要显式登记 |
| 情节漂移 | 场里有来源没有的事件 | 来源锚点 + brief 约束 + 人工抽读 |
| 长度崩塌 | 每场只有一句话/严重超长 | 目标时长 + 估算偏差警告 |
| 只写对白 | 没有动作/视觉信息 | 动作块非空检查；brief 要求外化 |
| 覆盖漏洞 | 某些章节/句子从未被改编 | 句子级覆盖检查 |
| 长程遗忘 | 人物关系/已知信息前后矛盾 | 人物状态字段（M1）+ 前后场摘要 |

---

## 8. 本子 repo 的 M0 范围

本调研直接支撑 `agents/screenplay-adapter/` 的 M0：

- `adapt`：解析小说 → 人物表 → 改编计划（场次/集/节拍/时长/来源锚点/覆盖）→ `adaptation.json` + `briefs.md` + 计划报告。
- `draft`：按 brief 逐场调用 OpenAI 兼容端点，草稿独立落盘，带 prompt/source/plan 指纹；失败可续跑。
- `assemble`：合并草稿 → `screenplay.json` → Fountain/Markdown → 验收报告。
- `validate`：重跑计划/剧本门，输出 `pass` / `warn` / `fail`。

不在 M0：人物状态机、因果关系图、对白质量模型评分、分镜/机位、双人对白、自动改写循环、UI。
