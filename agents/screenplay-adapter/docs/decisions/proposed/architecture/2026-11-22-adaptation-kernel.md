# 决策：先做确定性改编计划，再做逐场写作

状态：proposed

## 问题

把小说改编成剧本，最自然的做法是“把全文和一个 prompt 交给模型，让它直接写剧本”。调研（[`docs/research/2026-11-novel-to-screenplay-survey.md`](../../../../../../docs/research/2026-11-novel-to-screenplay-survey.md)）显示这条路在长文上会同时遇到四个问题：

1. 上下文放不下整本小说；截断或摘要会丢情节，模型还会补出不存在的剧情。
2. 长程一致性差：人物关系、已知信息、时间线容易漂移；STAGE 之类的评测显示模型会“静默遗忘”。
3. 一次性正文不可核对：某场写偏了，无法知道它对应原文哪里，也无法只重写这一场。
4. 制作约束（集数、单集时长、场次、人物、场景）不在模型的控制里，生成结果经常不可拍。

需要决定：这个子 repo 的第一个纵切做什么、哪些步骤由代码保证、哪些交给模型，以及工件如何组织。

## 决定

1. **计划先行，计划是事实源**：`adaptation.json` 先确定场次边界、来源区间、集、目标时长、结构节拍和在场人物；`screenplay.json` 是逐场草稿按计划合并的结果。Fountain/Markdown 只是视图。模型不能改计划。
2. **代码负责可计算的部分**：章节/段落/句子解析、字符偏移、人物抽取的候选、场次分配、覆盖、时长、集号、格式、哈希和门。模型只负责每场的动作和对白。
3. **章节优先的场次切分**：场数够时每章至少一场、章内再分；场数不够时合并相邻章节。这样场次边界不会落在章节标题中间，来源锚点能直接用于 brief 和审阅。
4. **人物抽取是建议，显式人物表是权威**：中文没有大小写，`说/道/问/答` 在叙述里大量出现；默认只用“引号附近 + 引号外”的对白归属抽候选，并支持 `--cast` 覆盖。对白说话人必须在人物表中；新角色先改人物表。
5. **结构模板是数据**：长片用 15 拍近似区间，短剧/剧集用每集“钩子—升级—反转/复杂化—卡点”。模板用于分配场次和检查节奏，不用于判断故事好坏；换模板是加一份列表，不是加分支。
6. **一次只写一场，草稿独立落盘**：prompt 只带本场原文、人物表、前后场摘要、节拍、时长和硬约束；每场写 `drafts/S*.json`，带计划/原文/prompt 指纹（计划哈希覆盖源、brief、人物表、场次）。计划或原文变化后旧草稿拒绝合并；重写是显式 `--force`。源文本是大纲/短篇时用 `--mode expand`，让每场 brief 明确要求补动作/反应/对白；内核仍不替模型发明情节。
7. **确定性门分 fail / warn**：覆盖断裂、场次/集缺失、人物越权、格式坏、计划指纹不匹配是 fail；时长估算偏差、无对白、新增比例高、草稿人物与计划检测不一致是 warn。语义质量不自动判分，留给人工。
8. **对白必须标来源**：`source` / `adapted` / `invented`。改编必然新增对白，不禁止，但必须披露；新增比例只做 warning，避免用模型自评替代人审。
9. **先 OpenAI 兼容协议，不绑定供应商**：`writer.py` 用标准库发 chat-completions 请求，记录 provider/model；不引入 SDK。测试用本地假 server，不访问网络。
10. **技术栈**：Python 3.12+，无第三方运行时依赖；JSON 为事实源，Fountain 为交换/人读格式。

## 备选方案

- **整本小说一次 prompt 出剧本**：实现最快，但长文截断、不可核对、不能局部重写；与“可核对、可编辑”目标冲突，否决。
- **先摘要再写**：摘要会丢因果和细节，且摘要本身不可核对；只适合作为 M1 的滑窗/情节图预处理，不作为主路径。
- **用微调模型直接学小说→剧本**：需要数据和训练资源，输出仍不可审计；当前没有数据规模和评估条件，否决。
- **Fountain 作为事实源**：人读友好，但难以表达来源区间、场次目标、人物引用和计划哈希；解析富文本做校验会引入第二套语法。否决，改为 JSON → Fountain 视图。
- **复用 auto-shot 的“剧本还原”schema**：那是从成片 ASR/标签反推的分析产物，字段语义不同；共享类型会把两个方向的演化绑死。否决，只保留版本化 JSON 交换。
- **先做 UI/编辑器**：没有稳定计划和 schema 时 UI 会返工；先 CLI + 工件。
- **场时长按原文长度加权**：更像“按素材量分配”，但会把冗长叙述变成冗长场次；M0 用均分，扩写/压缩用 flag 提示，M1 再引入戏剧权重。

## 后果

- 首个纵切没有“自动写出好剧本”的能力，只有可核对的结构和逐场草稿；短期看起来慢，但覆盖、人物和来源问题能在写之前暴露。
- 场次边界和人物表的质量取决于输入和显式覆盖；中文自动抽人物会有漏抽/误抽，重要项目必须用 `--cast`。
- 均分场时长是刻意粗糙的默认值；长片/短剧的真实节奏需要 M1 的权重和人工调整。
- 计划哈希会让“改原文/改 brief/改人物表后旧草稿全部失效”成为显式行为；这是有意的，避免静默混用版本。
- 结构模板带有商业长片/短剧的偏好；文艺片、群像、实验叙事需要换模板或手工改计划。
- 语义质量仍要人读；门只能保证“结构上可交付”，不能保证“好看”。
