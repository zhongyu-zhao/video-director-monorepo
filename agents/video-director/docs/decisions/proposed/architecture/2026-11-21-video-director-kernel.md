# 决策：video-director agent 的确定性内核与 artifact-first 编排

状态：proposed

## 问题

video-director 要把创作意图变成可核对、可编辑、可导出的视频产物。调研（`docs/research/2026-11-video-agents-survey.md`）的结论是：生产级项目普遍采用“代码管骨架、模型做决策”的混合控制流；一次性吐 MP4 的项目第二次修改就要重来；时间线是能否进入真实工作流的分水岭。

需要决定：先做什么、状态放哪里、哪些步骤由代码保证、哪些交给模型，以及如何避免被单一生成模型或渲染器锁死。

## 决定

1. **先确定性内核，再 agent 外壳**：M0 先做项目/资产/时间线/版本内核（`Project → Asset → TimelineClip → Revision`），再在 M2 随规划层引入 `Scene → Shot`；渲染先做 FFmpeg/EDL，随后是 JSON 工件和版本历史；M1 做工具层；M2 做代码 DAG 编排；M3 做质检；M4 做 skill 化。没有稳定内核之前，不先做 UI 或生成能力。
2. **时间线是唯一事实源**：分镜/镜头表是可编辑层，预览和成片都从时间线渲染。修改走“工具 + receipt + revision”，不允许 LLM 直接改 JSON 或直接输出最终视频。
3. **工件即状态**：项目目录固定为 `project.json` + `artifacts/` + `assets/` + `renders/` + `history/`。每个阶段读上一阶段工件、做 schema 校验、写 checkpoint；失败可断点续跑。被覆盖的版本归档到 `history/`，不丢审批轨迹。
4. **混合控制流**：阶段骨架用代码 DAG；阶段内的创意决策、候选比较和异常重规划用 LLM。纯 LLM 编排只适合个人助理场景，不作为主路径。
5. **供应商解耦**：把能力（生成图像、生成视频、TTS、分析、检索）和 provider 分开；provider adapter 统一描述、错误和成本。成本账本记录 estimate / reserve / reconcile，支持 `observe / warn / cap`，默认有单次和总预算上限。
6. **一致性与质检**：角色/场景资产化并注册参考图；需要跨镜头一致性时用首尾帧、参考图和 best-of-N + VLM 评审；交付前做确定性 QC（ffprobe、抽帧、音频电平、字幕）和人工 gate。确定性检查先于模型评审。
7. **与 auto-shot 解耦**：不共享代码。可以把 auto-shot 导出的 `shots.json` 作为可选输入，但必须按本项目的版本化契约校验；没有 auto-shot 也能独立运行。
8. **技术栈**：Python 3.12+ 与 FFmpeg 作为内核。渲染器可插拔：先 FFmpeg（剪辑、拼接、混音、字幕），需要排版/动效时再引入 Remotion/HTML；Web UI 不阻塞内核。
9. **首个纵切（本 PR）**：`project init` / `validate` / `render`。项目模型 + 时间线校验 + 本地素材的确定性拼接 + ffprobe 验收。规划、生成、质检、多轨和时间线编辑留给后续 PR。

## 备选方案

- **LLM agent 自由调用工具、直接产出成片**：灵活，但不可复现、不可恢复、成本不可控，不作为主路径。
- **一次性生成 MP4、不保存时间线**：实现最快，但任何修改都要重来，与“可编辑”目标冲突，否决。
- **绑定单一生成 provider 或 Remotion**：开发和演示快，但换供应商或换渲染语法就要重写；内核必须与它们解耦。
- **先做 UI/交互**：在没有稳定项目模型和时间线时，UI 会随内核返工；先 CLI + 工件。
- **用数据库做项目状态**：事务和查询更强，但 diff/review/版本管理差；MVP 用 JSON + 版本历史。

## 后果

- 首个纵切没有“创作”能力，只是一条可验证的渲染内核；短期看起来慢，但后续的规划、生成、质检都能挂在这条骨架上。
- `project.json`、时间线工具和质检报告会成为长期接口，必须严格版本化；破坏性变更需要 migration。
- FFmpeg 表达力有限；排版、数据可视化、复杂动效需要后续渲染器，届时会增加一层渲染抽象。
- 人工 gate 会降低自动化程度；这是有意为之，因为生成视频的成本和不可控性都很高。
