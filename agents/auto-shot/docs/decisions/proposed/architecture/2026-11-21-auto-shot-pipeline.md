# 决策：auto-shot agent 的四层流水线

状态：proposed

## 问题

自动拉片要输出“可核对、可编辑、可导出”的镜头表和逐镜分析。调研（`docs/research/2026-11-auto-shot-analysis-survey.md`）给出的核心事实是：VLM 会编时间码、漏镜、前后矛盾；整部电影塞不进一次上下文；而镜头切分、时长、运动量这些事实已经可以用 CV 稳定测量。

需要决定：哪些环节交给模型、哪些由代码保证，控制流怎么走，状态放在哪里，以及失败后如何恢复。

## 决定

1. **四层分离**：机器测量 → 模型判断 → 代码验收 → 人审/交付。镜头边界、时长、帧率、运动量、亮度、色彩、人脸比例等事实只由代码写入 `measured`；VLM 只填写枚举标签、画面描述、叙事功能、证据和置信度。
2. **控制流是代码 DAG，不是 LLM 自由编排**：`ingest → detect → evidence → label → scenes → report`，每个阶段读取上一阶段工件、写出自己的工件，失败可只重跑该阶段。LLM 只在阶段内部做判断，不负责决定“下一步做什么”。拉片是覆盖和一致性问题，不是检索问题；批处理 + 分层 reduce 比“边看边找”的 agent 循环更合适。
3. **工件即状态**：`media.json`、`shots.json`、`scenes.json`、`report.md`、`quality.json` 都是版本化文件。模型批处理可以写中间缓存（如 `labels/`），但合并后的 `shots.json`（含测量、标签、证据）是唯一事实源，报告只是它的一个视图；播放器、CSV、HTML、问答都从同一份镜头表生成。
4. **镜头卡分层字段**：`measured`（代码）、`labels`（模型枚举）、`content`（模型描述）、`function`（模型 + 上下文）、`evidence`、`confidence`、`provenance`（检测器/模型/prompt 版本、`detected`/`manual`）。字段契约见 `docs/decisions/proposed/architecture/2026-11-21-shot-table-contract.md`。
5. **批处理 + 分层 reduce**：逐镜标注按 20–25 镜一批，配联系表；先出镜头卡，再聚场景，最后写全片报告。不把整片塞进单次调用，也不要求旗舰模型刷上千个镜头。
6. **幂等与增量**：缓存 key 由 `video_hash + shot_hash + prompt_version + model` 组成；人工改过的切点或标签标记为 `manual`，后续自动重跑不覆盖。重跑只影响变更的下游。
7. **质量门**：时间轴连续、镜号连续、时长自洽、枚举合法、每个标签有证据、运动与实测一致、描述可核对、主体可对账。没有证据的门只能标 `skipped`，不能算 `passed`；低置信度进入“待人工确认”，不直接算完成。
8. **运行形态**：本地优先的 CLI / 批处理。模型通过 provider adapter 注入，MVP 不依赖商业视频 API；帧和音频默认不外传。
9. **模块边界**：`probe`、`detect`、`measure`、`label`、`scenes`、`report` 各自独立，`pipeline` 只负责编排；核心数据结构放 `models`，不引入全局状态。

## 首个纵切（本 PR）

只实现 M0：`ffprobe` 读取媒体信息 → `ffmpeg` 场景检测出候选切点 → 生成 `shots.json` → 时间轴/镜号/时长质量门 → Markdown 镜头表报告。逐镜 VLM 标注、场景聚合、交互报告留给后续 PR。

首个纵切验证两件事：镜头表可以作为唯一事实源；工件、质量门和 CLI 的骨架能跑通。它刻意不做“影评”，避免在事实层还不稳时先做解释层。

## 备选方案

- **单次 VLM 整片分析**：便宜、开发快，但时间码、覆盖和一致性都不可控，只能做 demo，否决为主路径。
- **LLM agent 自由编排工具**：能处理开放需求，但不可复现、贵、容易“说做了其实没做”。M4 可以在镜头表之上加问答/检索层，但不承担主流水线。
- **纯 CV 无 VLM**：能产出技术参数表，无法解释视听语言，作为测量层保留，不构成完整产品。
- **商业 API 一体化**：Google、Azure、AWS、Twelve Labs 只给段和标签，解释层仍要自己做，还带来数据外传、成本和供应商锁定。作为可插拔的检测/ASR provider，不作为内核。

## 后果

- 工程量大：测量、schema、质量门、缓存、人工 recut 都要自己写；换来的是可核对、可恢复、可增量。
- 首个纵切还回答不了“这一镜为什么这样拍”；报告在 M2 之前只有事实层，这是有意的顺序。
- 强依赖 `ffmpeg`/`ffprobe`，README 和子 repo `AGENTS.md` 记录版本要求。
- Python 是测量、CV 和 VLM 生态最顺的选择；代价是未来若做浏览器端交互报告，需要额外的 Web 层，而不是复用一套前端框架。
